# Cleanstartup Stack

The Cleanstartup Stack is an opinionated technical foundation for building startup artifacts, such as products, content and operational tooling.

## Goals

The Cleanstartup Stack is guided by three goals.

### Keep Artifact Maintenance Low

Artifacts built with the stack should remain maintainable for a long time without frequent migrations to the next major framework, library, language or build tool version.

The stack therefore favors established technologies, conservative ecosystems and web standards, so technical founders can focus on the actual customer need rather than repeatedly reworking technical foundations.

### Make Knowledge Worth Accumulating

The stack prefers a few broadly useful tools over many specialized tools.

This makes knowledge, patterns and improvements more valuable over time because they can be applied across many different artifacts.

### Make Reuse Easy

Artifacts should not be forced to share everything. But when shared code, content, styles or components make sense, reuse should require little additional effort.

This helps maintain consistency across artifacts, from behavior and language to visual presentation and brand expression.

## Core Concepts

The Cleanstartup Stack is organized around Targets, Assets and Stack Modules.

### Targets Define How an Artifact Is Used

A Target defines how an Artifact is built, run or delivered.

Typical Targets include Webapps, Websites and CLIs.

A Target is created from a root Stack Module. The root Stack Module defines the capabilities available to the Target and may include other Stack Modules.

### Assets Make Resources Available to Targets

Assets are resources that may be used by Targets.

Typical Assets include compiled CSS, JavaScript bundles, copied static files, generated HTML, images and fonts.

Assets may be relevant to some Targets and irrelevant to others. For example, UI-related Assets may be used by Webapp and Website Targets while being ignored by a CLI Target.

Assets are created from Asset Sources. Depending on their type, creating Assets may involve compilation, transformation, copying or referencing. Asset Sources are committed to Git. Built Assets are not.

Targets receive Asset Sources only from the root Stack Module and the Stack Modules included by it. Transitive Go dependencies do not automatically contribute Asset Sources. This keeps the build explicit: Go dependencies can provide reusable code, but UI and content sources only become part of an Artifact when a Stack Module includes them deliberately.

### Stack Modules Bundle What Belongs Together

In this document, a Stack Module refers to a Cleanstartup Stack Module, not a Go module.

A Stack Module groups related business logic, Asset Sources, npm-compatible dependencies and included Stack Modules. It defines what belongs together and what is ultimately made available to Targets.

Since Asset Builds are often directly tied to a parent directory, not more than one Stack Module shall be defined per directory. However, the same Artifact may contain multiple Stack Modules.

Each Stack Module has a unique, dot-separated name that also serves as its namespace. Reverse-domain names such as `xyz.cleanstartup.blog` are strongly recommended but not enforced.

## Technology

The stack uses a small, integrated set of technologies that can be applied across different artifact types without turning every artifact into a separate technical universe.

### Go as the Application and Build Foundation

Go is the foundation of the stack because it is simple, stable and broad enough to cover many parts of a startup artifact without introducing a large amount of additional tooling.

Each Target corresponds to its own Go command under `cmd/...` and contains exactly one `main` function. The stack also uses Go as the primary definition language for Stack Modules and Asset Sources. It derives the required build setup from those definitions, allowing reuse to happen through the normal Go dependency system.

Go is used for business logic, backend development and frontend delivery. For Webapps, Go provides the server-side application layer. The stack uses `templ` to define HTML components as regular Go code, so application UI can be composed together with backend logic, routing and delivery.

Generated Go code, including code generated by `templ`, is committed to Git. This keeps packages directly usable as Go dependencies without requiring consumers to install additional generators or run preparatory build steps.

### Tailwind CSS for Consistent Styling

Tailwind CSS is the default for styling and theming because it provides an established system for implementing a consistent visual language.

Tailwind is used together with Stack Modules and Asset Sources, so reusable building blocks can contribute styling where it belongs instead of requiring every Target to define everything from scratch.

The stack is intended to add target-specific Tailwind variants so that components can later adapt their presentation to different output formats.

### Stencil and Web Components for Interactive UI

Stencil is used to create interactive UI components based on the Web Components standard. It also provides tooling for static rendering, which supports the later reuse of suitable components in static Targets such as PDFs.

Components may provide small enhancements or extensive interactions, depending on the use case. However, they should provide an appropriate static representation where useful. Interactive-only parts may be simplified or omitted for static Targets.

Stack Modules may declare npm-compatible dependencies for their components. This allows a component to use an external frontend library when needed without making npm the primary configuration layer of the stack. For this, the stack generates a module-specific `package.json` when npm-compatible dependencies are needed. A module-specific `package-lock.json` may be committed to Git to keep those dependencies stable.

### Hugo and Markdown for Content-Driven Artifacts _(planned)_

Content-driven artifacts such as websites, blogs and documents are written in Markdown because it is widely established, easy for humans to read and write, and works well as a format that can be generated, transformed and maintained with AI-assisted workflows.

Hugo is used as a rendering engine because it fits naturally into a Go-based stack and provides a mature foundation for processing Markdown-based content.

## Usage

### Defining a Module

A Stack Module is defined by calling `stack.Bundle()` with a unique namespace and a list of parts. Parts may include Asset Sources, npm dependencies, HTTP mounts and other Stack Modules.

```go
// deps/branding/module.go
package branding

import (
	"github.com/cleanstartup/stack"
	"github.com/cleanstartup/stack/assets"
)

func Module() stack.Module {
	return stack.Bundle(
		"cleanstartup.branding",
		assets.Dir("."),                // CSS + Stencil sources in this directory
		assets.Use("alpinejs", "^3.0"), // npm dependency for components
	)
}
```

Modules can include other Modules. The root Module composes everything:

```go
func Module() stack.Module {
	return stack.Bundle(
		"example.app",
		assets.Dir("internal/web/ui"),
		branding.Module(),
	)
}
```

A Target is activated by calling `WebApp()` on the root Module. The options passed to `WebApp()` declare which asset builders are active for this Target.

```go
// cmd/app/main.go
package main

import (
	"github.com/cleanstartup/stack/assets"
	"example.com/myapp"
)

func main() {
	myapp.Module().WebApp(assets.Tailwind(), assets.Stencil())
}
```

This starts the app-specific CLI with `install`, `build`, `dev` and `run` commands.

### Asset Sources

The `assets` package provides the building blocks for declaring Asset Sources within a Stack Module.

| Function | Purpose |
|---|---|
| `assets.Dir(relPath)` | Declares a directory as a source for Tailwind CSS and Stencil components. Synced to `.sources/<namespace>/` during `install`. |
| `assets.StaticDir(relPath)` | Copies a directory to the asset output as-is, without processing. |
| `assets.Use(name, version)` | Declares an npm-compatible dependency for Stencil components. |
| `assets.Tailwind()` | Passed to `WebApp()` to activate the Tailwind CSS builder. |
| `assets.Stencil()` | Passed to `WebApp()` to activate the Stencil component builder. |

`assets.Dir()` is a descriptor: it records the caller's directory at definition time and resolves to an absolute path at composition time. No filesystem access happens until `install` or `build` runs.

Tailwind picks up `*.tailwind.css` files within a declared `Dir`. All declared directories are also added to Tailwind's content scan so utility classes used in `.go`, `.templ`, `.html` and `.tsx` files are included. Stencil picks up `*.stencil.ts` and `*.stencil.tsx` files.

Tailwind produces a single output at `/assets/css/app/app.css`. Stencil produces a single output at `/assets/js/stack/stack.esm.js`.

### Commands

Each Target exposes four commands via its `main` function:

```
go run ./cmd/app install   # prepare workspace and sync sources
go run ./cmd/app build     # build assets and binary
go run ./cmd/app dev       # start development environment
go run ./cmd/app run       # serve already-built assets
```

**`install`** syncs declared `Dir` sources to `.sources/<namespace>/` and installs npm dependencies into the workspace. Run this after adding a new Module or npm dependency.

**`build`** materializes all Asset Sources, runs Tailwind and Stencil, writes outputs to `.assets/` and compiles the current command binary into `cmd/<name>/.bin/<name>`.

**`dev`** runs `install` and `build`, then starts Tailwind and Stencil watch workers, serves the application over HTTP and broadcasts a live-reload signal to connected browsers whenever output files settle after a change. When Go source files change, a restart hint is logged.

**`run`** serves already-built assets from `.assets/` without rebuilding. Expects `build` to have run first.

All commands support `--help`. Calling the binary without a command shows help.

### CLI Target

A CLI Target is a standalone command-line application. It is defined with `stack.CLI()` and activated by calling `CLIApp()`.

```go
// internal/cli/cli.go
package cli

import (
    "github.com/cleanstartup/stack"
    stackcli "github.com/cleanstartup/stack/cli"
)

func CLIModule() stack.CLIModule {
    return stack.CLI(
        stackcli.Group("setup",    checkCmd, encryptionCmd),
        stackcli.Group("codebook", discloseCmd),
        stackcli.Group("user",     importCmd, syncCmd),
    )
}

// cmd/cli/main.go
func main() { cli.CLIModule().CLIApp() }
```

### Params

Parameters are declared as typed descriptors and read inside handlers using `activity.Param`. The same declaration works across CLI and web handlers.

```go
import (
    "github.com/cleanstartup/stack/activity"
    "github.com/cleanstartup/stack/param"
    stackcli "github.com/cleanstartup/stack/cli"
)

var userID  = param.String("user-id", param.Required[string]())
var verbose = param.Bool("verbose", param.WithDefault(false))
var mnemonic = param.String("mnemonic",
    param.Required[string](),
    param.WithPrompt[string]("Decryption Key (Mnemonic): "),
)

var showUserCmd = stackcli.Activity(
    "show",
    func(inv *stackcli.Invocation) struct{} { return struct{}{} },
    func(ctx stackcli.Context[struct{}]) stackcli.Result {
        id      := activity.Param(ctx, userID)
        verbose := activity.Param(ctx, verbose)
        ctx.Stdout("user=%s verbose=%t\n", id, verbose)
        return stackcli.Done()
    },
)
```

| Constructor | Type | Options |
|---|---|---|
| `param.String(name, opts...)` | `Param[string]` | `Required`, `WithDefault`, `WithAlias`, `WithPrompt` |
| `param.Int(name, opts...)`    | `Param[int]`    | `Required`, `WithDefault`, `WithAlias` |
| `param.Bool(name, opts...)`   | `Param[bool]`   | `Required`, `WithDefault`, `WithAlias` |

`WithPrompt` is supported by CLI handlers. When the flag is not provided, the user is asked interactively. Web handlers ignore the prompt and return the default.

## Packages

- `stack`: root package — `Bundle`, `Extend`, `CLI`, `Assets`, `Mount`, `CSS`, `JS`, `File`
- `assets`: asset source descriptors — `Dir`, `StaticDir`, `Use`, `Tailwind`, `Stencil`
- `param`: typed parameter descriptors — `String`, `Int`, `Bool`, `Required`, `WithDefault`, `WithAlias`, `WithPrompt`
- `activity`: typed activity definitions, instances, URI building, `Param[T]()` helper
- `web`: HTTP registration, routing, asset pipelines and request decoding; implements `param.Resolver`
- `cli`: command registration, `Group()`, `BuildRegistry()`, help text and execution; implements `param.Resolver` and `param.Prompter`
- `config`: env-based config loading with `.env` support

## Environment Variables

| Variable | Purpose |
|---|---|
| `STACK_TAILWIND_BINARY` | Path to a local Tailwind binary |
| `STACK_TAILWIND_VERSION` | Tailwind version to download if binary is absent |
| `STACK_TAILWIND_CACHE_DIR` | Directory for the downloaded Tailwind binary |
| `STACK_TAILWIND_DOWNLOAD_BASE` | Override the GitHub release download base URL |
| `STACK_STENCIL_BINARY` | Path to a local Stencil CLI binary |
